

## 1. Purpose

Документ определяет нефункциональные требования к SplitOS.

Нефункциональные требования описывают свойства системы, которые должны сохраняться независимо от конкретного пользовательского сценария:

- производительность;
    
- стабильность;
    
- надёжность;
    
- безопасность переходов между режимами;
    
- восстановление;
    
- совместимость;
    
- управляемость обновлений;
    
- пользовательский опыт;
    
- использование ресурсов;
    
- наблюдаемость;
    
- расширяемость;
    
- сопровождаемость;
    
- безопасность пользовательских данных.
    

Документ не определяет внутреннюю архитектуру SplitOS и конкретные технологии реализации.

# 3. General quality principle

SplitOS является агрессивно оптимизированным управляемым дистрибутивом, однако оптимизация не должна достигаться ценой непредсказуемого поведения системы.

Главный принцип:

> SplitOS должен удалять, отключать и изменять только те системные элементы, для которых известно влияние на поддерживаемые пользовательские сценарии.

Для каждого значимого системного изменения в дальнейшем должны быть определены:

```text
Reason
Expected effect
Affected area
Compatibility impact
Reversibility
Recovery behavior
Validation method
```

# 5. Game performance stability

## NFR-PERF-100

При автоматической оптимизации игры приоритетом должна быть стабильность производительности, а не достижение кратковременного максимального FPS.

---

## NFR-PERF-101

SplitOS должен стремиться подобрать максимально возможное качество изображения при возможности поддерживать производительность, соответствующую целевому игровому профилю.

Концептуально:

```text
maximize Visual Quality

while

Stable FPS >= Target FPS
```

---

## NFR-PERF-102

Если Target FPS объективно недостижим на текущем оборудовании, SplitOS должен стремиться получить максимально высокий стабильный FPS при допустимом качестве изображения.

---

## NFR-PERF-103

Target FPS должен учитывать характеристики активного Game Display.

В том числе:

```text
refresh rate
resolution
VRR capability
```

---

## NFR-PERF-104

Изменение оборудования или активного игрового дисплея должно приводить к повторной проверке актуальности Game Profile до запуска соответствующей игры.

---

# 6. Mode isolation

## NFR-REL-001

Work Mode и Game Mode должны быть взаимоисключающими активными состояниями.

Недопустимое состояние:

```text
WORK_ACTIVE
+
GAME_ACTIVE
```

---

## NFR-REL-002

После успешной активации Work Mode необязательные компоненты Game Mode не должны оставаться активными.

---

## NFR-REL-003

После успешной активации Game Mode необязательные компоненты Work Mode не должны оставаться активными.

---

## NFR-REL-004

Общие компоненты должны явно классифицироваться как допустимые в обоих режимах.

---

## NFR-REL-005

SplitOS должен иметь возможность определить, в каком режиме система фактически находится.

Режим не должен считаться успешно активированным только на основании того, что пользователь нажал соответствующую кнопку.

---

# 7. Mode transition reliability

## NFR-TRANS-001

Переход между режимами должен рассматриваться как управляемая операция изменения системного контекста.

---

## NFR-TRANS-002

Перед переходом:

```text
Work Mode → Game Mode
```

SplitOS должен проверить наличие состояний, которые могут сделать переход небезопасным.

Например:

```text
unsaved documents
active local servers
active development environments
long-running tasks
protected processes
critical user operations
```

---

## NFR-TRANS-003

Наличие критического блокирующего состояния не должно приводить к безусловному уничтожению пользовательского процесса.

---

## NFR-TRANS-004

Если безопасное разрешение блокирующего состояния невозможно автоматически, SplitOS должен запросить решение пользователя.

---

## NFR-TRANS-005

Пользователь должен иметь возможность отменить переход в Game Mode до начала необратимых действий.

---

## NFR-TRANS-006

При отмене перехода система должна сохранить Work Mode как активное состояние.

---

## NFR-TRANS-007

Если игра была запущена до завершения подготовки Game Mode и переход отменён, игровой запуск должен быть остановлен или отменён там, где это технически возможно.

---

## NFR-TRANS-008

При ошибке одного из этапов перехода SplitOS не должен без дополнительной обработки продолжать переход как полностью успешный.

---

## NFR-TRANS-009

Результат перехода должен быть одним из определённых состояний:

```text
SUCCESS
CANCELLED
ROLLED_BACK
FAILED_WITH_SAFE_FALLBACK
```

Неопределённое промежуточное состояние считается дефектом.

---

# 9. Startup and session behavior

## NFR-REL-100

После стандартного Windows sign-in SplitOS должен восстановить собственный пользовательский и лицензионный контекст до перехода к выбору режима.

---

## NFR-REL-101

Пользователь не должен автоматически попадать в Work Mode или Game Mode до определения требуемой startup policy.

Базовая концепция предусматривает выбор режима после входа.

---

## NFR-REL-102

Ошибка SplitOS на этапе выбора режима не должна делать компьютер полностью недоступным для восстановления.

---

## NFR-REL-103

Должен существовать безопасный fallback-механизм входа в систему при невозможности загрузить пользовательский SplitOS-контекст.

Точная реализация определяется позднее.

---

# 10. Game Launcher reliability

## NFR-REL-200

SplitOS Game Launcher должен быть доступен после успешной активации Game Mode.

---

## NFR-REL-201

Неисправность одной интеграции с внешним Game Client не должна приводить к полной недоступности Game Launcher.

---

## NFR-REL-202

Недоступность одного Game Client не должна блокировать запуск игр из других поддерживаемых клиентов.

---

## NFR-REL-203

Game Launcher должен корректно обрабатывать состояние:

```text
client unavailable
client not authenticated
game unavailable
game updating
game missing
integration error
```

без завершения всего Game Mode.

---

## NFR-REL-204

После завершения игры пользователь должен возвращаться в стабильный Game Mode / Game Launcher context.

---

## NFR-REL-205

Закрытие игры не должно автоматически переводить пользователя в Work Mode.

---

# 11. External Game Client isolation

## NFR-REL-300

Ошибка внешнего Game Client не должна нарушать базовую работоспособность SplitOS.

---

## NFR-REL-301

SplitOS не должен считать локальную копию состояния Game Client абсолютным источником истины при наличии возможности проверить фактическое состояние клиента.

---

## NFR-REL-302

Интеграции с различными Game Clients должны быть максимально изолированы друг от друга.

---

# 12. Shared Apps

## NFR-PERF-200

Game Mode должен ограничивать количество одновременно активных Shared Apps.

Для текущей концепции:

```text
maximum active Shared Apps = 3
```

---

## NFR-PERF-201

Ограничение относится к приложениям, которым SplitOS предоставляет активное Game Mode представление.

Например:

```text
Browser
Discord
Spotify
```

---

## NFR-PERF-202

Shared App может быть представлен как:

```text
Overlay
Locked window
Secondary display
Background application
```

---

## NFR-PERF-203

Открытие Shared App не должно необоснованно менять Game Profile текущей игры.

---

## NFR-PERF-204

Shared Apps не должны получать приоритет над игровым процессом без явного пользовательского действия или системной необходимости.

---

# 13. Display compatibility

## NFR-COMP-001

SplitOS должен работать со всеми дисплеями, которые корректно обнаруживаются поддерживаемой Windows-конфигурацией.

---

## NFR-COMP-002

Поддержка конкретной функции дисплея должна определяться фактически сообщаемыми возможностями устройства и драйвера.

---

## NFR-COMP-003

SplitOS не должен предполагать наличие:

```text
HDR
VRR
high refresh rate
specific resolution
```

без подтверждения со стороны системы.

---

## NFR-COMP-004

Подключение или отключение дисплея не должно приводить к необратимой потере пользовательского display profile.

---

## NFR-COMP-005

При недоступности целевого Game Display должен применяться безопасный fallback.

---

## NFR-COMP-006

Пользователь должен сохранять возможность вручную переопределить выбранный SplitOS display profile.

---

# 14. Input compatibility

## NFR-COMP-100

Input subsystem должен поддерживать переключение между:

```text
Keyboard & Mouse
Controller
```

без обязательной перезагрузки системы.

---

## NFR-COMP-101

Подключение нового устройства ввода не должно нарушать работу уже активных устройств.

---

## NFR-COMP-102

Game Mode UI должен быть полностью доступен через поддерживаемый Controller profile для основных игровых сценариев.

---

## NFR-COMP-103

Keyboard & Mouse должны оставаться доступными в Game Mode даже при использовании controller-first UX.

---

## NFR-COMP-104

SplitOS не должен подменять игровой input там, где игра самостоятельно корректно обрабатывает выбранное устройство.

---

# 15. Game profile consistency

## NFR-REL-400

Game Profile должен однозначно относиться к:

```text
Game
Hardware context
Display context
Input context
```

---

## NFR-REL-401

Одна игра должна иметь возможность иметь несколько профилей.

Например:

```text
Desktop / 1440p / 280 Hz / Keyboard & Mouse

TV / 4K / 60 Hz / Controller
```

---

## NFR-REL-402

Изменение одного Game Profile не должно неконтролируемо изменять другой профиль той же игры.

---

## NFR-REL-403

Перед запуском игры SplitOS должен проверять актуальность аппаратного контекста относительно сохранённого профиля.

---

## NFR-REL-404

Если значимых изменений не обнаружено, Game Profile не должен пересчитываться без необходимости.

---

## NFR-REL-405

Если аппаратный контекст изменился, SplitOS должен иметь возможность обновить рекомендации до запуска игры.

---

# 16. User control over game optimization

## NFR-UX-001

Автоматическая оптимизация должна требовать минимального количества пользовательских решений.

---

## NFR-UX-002

При наличии проверенного Game Profile SplitOS должен иметь возможность применить его автоматически.

---

## NFR-UX-003

Автоматически выбранные настройки не должны быть заблокированы от ручного изменения пользователем.

---

## NFR-UX-004

Пользователь должен иметь возможность изменить параметры непосредственно в игре.

---

## NFR-UX-005

SplitOS не должен автоматически отменять ручные изменения пользователя во время текущей игровой сессии.

---

## NFR-UX-006

Политика поведения SplitOS после обнаружения ручного изменения должна быть определена на этапе Analysis & Design.

---

# 17. Game Mode UX

## NFR-UX-100

Game Mode является основным UX-приоритетом первой версии SplitOS.

---

## NFR-UX-101

Основные Game Mode действия должны быть доступны без обязательного использования клавиатуры и мыши.

---

## NFR-UX-102

Пользователь должен иметь возможность из Game Launcher выполнять основные действия:

```text
select game
launch game
change game profile
change display
change input profile
access Shared Apps
return from game
switch to Work Mode
```

---

## NFR-UX-103

Типовые игровые действия должны требовать минимального количества переходов между SplitOS UI и интерфейсами внешних Game Clients.

---

## NFR-UX-104

SplitOS должен скрывать необязательные технические детали внешних клиентов там, где это возможно без нарушения их контрактов.

---

## NFR-UX-105

UI должен быть пригоден для использования на:

```text
desktop monitor
gaming monitor
television
```

---

## NFR-UX-106

Интерфейс Game Mode должен учитывать управление с дистанции, характерной для использования телевизора.

---

В первой версии Work Mode не требует создания нового desktop UX.

---

## NFR-UX-201

---

## NFR-UX-202

---

# 19. Distribution integrity

## NFR-INSTALL-001

SplitOS должен распространяться как отдельный управляемый дистрибутив на базе Windows 11.

---

## NFR-INSTALL-002

Полноценная поддержка SplitOS не должна зависеть от состояния ранее установленной пользовательской Windows.

---

## NFR-INSTALL-003

Поддерживаемая установка должна начинаться с известного базового состояния дистрибутива.

---

## NFR-INSTALL-004

Удалённые или отключённые компоненты Windows должны быть одинаково определены для одной версии SplitOS distribution.

---

## NFR-INSTALL-005

Две установки одной версии SplitOS при одинаковой конфигурации не должны существенно различаться по базовому системному составу.

---

# 20. Windows Update policy

Microsoft Windows patches должны рассматриваться как изменения внешней базовой платформы.

---

## NFR-UPD-003

Перед включением Windows patch в SplitOS release должна быть выполнена проверка совместимости.

---

## NFR-UPD-004

Пользователь должен получать обновление базовой Windows в составе совместимого SplitOS release.

---

## NFR-UPD-005

Новая версия Windows не должна считаться поддерживаемой исключительно на основании её официального выпуска Microsoft.

## NFR-UPD-006

SplitOS release должен иметь однозначно определённую совместимую Windows base version.

# 23. Recovery

## NFR-REC-001

SplitOS должен иметь возможность восстановить систему после частично применённого Mode Transition.

---

## NFR-REC-002

Recovery не должен зависеть исключительно от нормальной работоспособности Game Launcher.

---

## NFR-REC-003

Должен существовать безопасный режим восстановления, доступный при неисправности пользовательского SplitOS UI.

---

## NFR-REC-004

Recovery должен иметь возможность определить последнюю известную корректную конфигурацию.

---

## NFR-REC-005

Приоритет recovery:

```text
User data integrity
        ↓
System bootability
        ↓
Known safe mode
        ↓
Profile restoration
        ↓
UX restoration
```

---

## NFR-REC-006

Системные операции с повышенными привилегиями должны выполняться только компонентами, которым такие привилегии действительно необходимы.

# 33. Result

Нефункциональная модель SplitOS строится вокруг нескольких ключевых принципов:

```text
Predictable system state
        ↓
Strict Work/Game isolation
        ↓
Safe transactional transitions
        ↓
Minimal background overhead
        ↓
Game-performance stability
        ↓
Hardware-aware experience
        ↓
Controlled distribution updates
        ↓
Recoverability
        ↓
User data protection
        ↓
Graceful degradation
```

SplitOS должен предоставлять более глубокий контроль над Windows, чем обычное desktop-приложение, но этот контроль должен быть:

```text
predictable
testable
recoverable
versioned
observable
```

Агрессивная оптимизация является свойством продукта, но не оправдывает непроверяемые или необратимые изменения системы.

После согласования нефункциональных требований следующим этапом следует перейти к **Analysis & Design**, начав с формальной модели состояний и переходов SplitOS.
